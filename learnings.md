# Learnings

## Durable Decisions

- Start with Chromium, not Safari. Chromium supports fast unpacked extension testing; Safari requires an Apple app and Xcode extension wrapper.
- Start with detect-and-copy, then add automatic save. Detection quality is the core product risk.
- Shape the MVP around final data models so the detector can feed the later desktop app.
- Treat YouTube and premium streaming platforms as unsupported in the product path.
- The sellable product is the desktop media archive app; the extension is a companion capture surface.
- Vite config files use Node APIs, so the extension TypeScript config must include Node type context alongside Chrome extension types.
- Define shared media records before detector behavior so extension layers and the later desktop app do not drift into incompatible shapes.
- Classify blocked/DRM-likely domains before extension matching so a protected platform URL cannot look supported just because it has a familiar media-looking path.
- Ignore segment files such as `.ts` and `.m4s` in the generic classifier because playlist/manifest URLs are more useful for `yt-dlp` than individual chunks.
- Chrome runtime fields and installed TypeScript package fields may not always line up. When needed, model optional runtime fields narrowly instead of weakening all Chrome types.
- Store detected media in `chrome.storage.session` for the MVP so the popup and background service worker share state without committing media URLs to durable browser storage.
- Web requests can arrive concurrently. Snapshot writes must be serialized per tab or one read/modify/write cycle can overwrite another.
- Put the media snapshot storage key and read/write helpers in shared code so popup and background code cannot silently drift.
- Typed test fixtures should satisfy the same Chrome API types as production code. If the test cheats the shape, it can hide integration assumptions.
- Popup tests should cover both success and failure states because clipboard access can fail even when the UI renders correctly.
- MV3 network observation alone is not enough for the MVP. A real Chrome run loaded the page and requested `sample.mp4`, but no snapshot was stored until the extension also had a content-script media-element fallback.
- The background network listener should watch only `http` and `https` URLs. Browser and extension-internal assets are not user media candidates and should not appear as unsupported archive items.
- A standalone `chrome-extension://.../popup.html` tab is useful for inspecting extension storage, but it is not proof of the real toolbar popup because Chrome treats that standalone page as the active tab.
- An explicit `popup.html?tabId=<id>` path is useful for automation/debugging because it proves popup rendering against a known tab snapshot without changing normal toolbar active-tab behavior.
- Clipboard writes from automated extension-page clicks can be blocked by Chrome. Treat that as a useful failure-state proof, not as human Copy proof.
- The popup should keep the last non-empty candidate list stable while it is open. Temporary storage can clear for privacy, but the visible Copy surface should not disappear out from under the user.
- Build the local receiver before wiring Save in the extension. The receiver contract can be proven independently, and the popup integration stays small.
- Keep the first receiver framework-free. Node's built-in HTTP server is enough for a tiny loopback API and avoids adding app-server decisions too early.
- The receiver should run `yt-dlp` with `spawn(command, args)`, not a shell string, so media URLs are passed as data instead of executable text.
- The receiver should bind to loopback and reject normal website origins. A random website should not be able to trigger local downloads through the user's browser.
- Store receiver job transitions as append-only JSONL for the MVP. It is inspectable, replayable, and easy to replace later with archive storage.
- Keep Copy beside Save. Save is the product path, but Copy remains the best fallback when the receiver is not running or `yt-dlp` needs manual inspection.
- The extension should poll receiver jobs only while the popup is alive. Close/unmount should cancel active polling instead of leaving hidden work in the popup process.
- Use `/private/tmp` only for smoke tests. Real default saves belong in `~/Movies/Dew MediArchive`.
- Separate job history from archive records. Jobs explain what happened operationally; archive records describe saved media for future search, dedupe, export, and gallery views.
- Hash completed files before marking the receiver job completed. A Save should not claim completion unless the first archive metadata record was written successfully.
- Show the saved output path in the popup, but keep it compact. Full filesystem paths are useful confirmation, but they can easily overwhelm a small extension popup.
- Start the library as a server-rendered receiver page. It is enough to prove archive visibility without adding a frontend build system or desktop wrapper yet.
- Treat archive metadata as untrusted when rendering HTML. Source URLs and page titles came from websites and must be escaped.
- A root `npm run dew` launcher is the right personal-tool bridge before a packaged desktop app. It can build/check/start the receiver without taking on signing, installers, or native permissions yet.
- Library search, filtering, sorting, and exports should read archive records, not job history.
- CSV export is a security surface. Escape spreadsheet formula prefixes in untrusted text before writing CSV cells.
- Duplicate handling in the personal-tool MVP can safely reuse an existing archive record for the same source URL. This is not final content-hash dedupe, but it avoids repeated downloads for the same saved source.
- Completed Save UI should point users back to the library because the library is now the durable archive surface.
- Save progress belongs in the receiver job model. The popup should poll structured job progress instead of parsing logs or guessing.
- `yt-dlp` needs `--progress` when spawned without a terminal; otherwise progress-template lines may not appear even though the download succeeds.
- Progress is best-effort. Small direct files may complete before percent updates are useful, so queued/downloading/completed states still matter.
- Keep media-specific titles separate from page titles and source URLs. `mediaTitle` helps users distinguish multiple videos on one page; `pageTitle` remains provenance for the browser page; `url` remains the real downloadable source.
- Network-only stream candidates may not have element context. The popup should use page title as a readable fallback before using the raw source URL as the title.
- Popup state is not durable by itself. Any user-visible long-running receiver job needs a session-backed job id so the popup can restore progress after being closed.
- For the personal MVP, a double-click launcher is enough to remove the normal Terminal workflow without taking on full app packaging yet.
- Downloadable candidates should render before unsupported observations. Unsupported items are useful transparency, but they should not lead the user's decision flow.

## Mistakes To Avoid

- Do not turn detection, downloading, metadata, and UI into one function.
- Do not key identity by external filename or source URL alone.
- Do not hide unsupported, expired, or partial media states.
- Do not log private URLs or page data while debugging.
- Do not build polished app surfaces before proving media detection.
- Do not place build tools in runtime dependencies; keep React runtime dependencies separate from Vite/TypeScript/dev tooling.
- Do not pass bare media URL strings across layers once a structured detection record exists.
- Do not treat `blob:` URLs as downloadable media URLs; they are browser-local object references and need the underlying network request instead.
- Do not make the popup re-scan the page. The background worker owns detection; the popup should read snapshots.
- Do not perform unqueued read/modify/write updates for per-tab detection snapshots.
- Do not let clipboard failures fail silently; copy errors should be visible in the popup.
- Do not treat runtime-passing tests as enough when TypeScript says the mock shape does not match the browser API.
- Do not count component tests as a substitute for the final real toolbar-popup smoke test.
- Do not remove the page media-element fallback just because `webRequest` exists; the fallback is what produced the first clean runtime `sample.mp4` candidate.
- Do not let the extension observe its own popup assets as media detections.
- Do not claim explicit-tab popup rendering is the same as a real toolbar-popup proof.
- Do not blindly replace a visible popup list with empty state just because session storage sent a clear event.
- Do not let arbitrary websites call the local receiver.
- Do not run `yt-dlp` through shell interpolation.
- Do not treat the receiver as archive storage. It is only the first save-job backend.
- Do not push a manually passing Save flow before automated popup tests, typecheck, build, docs, and changelog are updated.
- Do not use jobs.jsonl as the library source of truth. It contains retries and state transitions, not one clean record per saved item.
- Do not add an Open Folder button inside the extension yet. That belongs with a native app wrapper or explicit browser download/open permissions, not the current lightweight popup.
- Do not add client-side script to the local library until there is a real workflow that needs it.
- Do not treat source-URL reuse as final deduplication. Hash-based object storage still belongs to the later archive engine.
- Do not export job history as the user archive. Exports should come from archive records so retries and transient failures do not leak into the library.
- Do not invent fake percentages when `yt-dlp` has not reported a total. Show an indeterminate/downloading state or byte/speed details instead.
- Do not overwrite `pageTitle` with a guessed media label. That would make provenance worse and still would not solve multi-video identification cleanly.
- Do not show the same manifest URL twice in a media card unless no title, page title, or element index exists.
- Do not create a second receiver job just because the popup reopened. Resume polling the existing job id when one is known.
- Do not hide unsupported observations entirely while the detector is still maturing; keep them visible below the actionable candidates.
